# ຄູ່ມືບັນຊີ ແລະ ສິດເຂົ້າເຖິງ

> ອັບເດດຫຼ້າສຸດ 10 ພະຈິກ 2026: Login ສຳເລັດເຂົ້າ Dashboard ໄດ້ທັນທີ. ຜູ້ໃຊ້ຂໍເອົາໜ້າບັງຄັບປ່ຽນລະຫັດຜ່ານຄັ້ງທຳອິດອອກ; ບັນຊີໃໝ່, reset ແລະ ບັນຊີເກົ່າບໍ່ຖືກກັ້ນດ້ວຍ mustChangePassword ອີກ. ປ່ຽນລະຫັດຜ່ານໄດ້ໃນ `/account` ຕາມຄວາມຕ້ອງການ (6–128 ຕົວ). Username/Password, session, CSRF ແລະ resource permissions ຍັງກວດຈິງຕາມເດີມ. ຂໍ້ຄວາມ first-login gate ເກົ່າຂ້າງລຸ່ມເປັນປະຫວັດ.


> ອັບເດດ 10 ພະຈິກ 2026: ຕາມຄຳຂໍຫຼ້າສຸດ ໜ້າ Login ກວດ Username/Password ກັບ API ຈິງໃນທຸກໂໝດແລ້ວ. ເອົາການກົດຂ້າມແບບ preview ອອກ; `?auth=preview`, `VITE_ENABLE_UI_PREVIEW` ແລະ browser flags ເກົ່າບໍ່ສາມາດຂ້າມ Login. ສ່ວນອະທິບາຍ preview ເກົ່າຂ້າງລຸ່ມເປັນປະຫວັດການພັດທະນາ.
> ໃນ local HTTP development ຮອງຮັບ `localhost`, `127.0.0.1`, `[::1]` ສະເພາະ port ທີ່ຕັ້ງ `APP_ORIGIN`; ຍັງກວດ CSRF ແລະ ປະຕິເສດ cross-site. Production ເຊື່ອໃຈສະເພາະ HTTPS origin ທີ່ຕັ້ງໄວ້.


## ເລີ່ມຕົ້ນ

ຫຼັງ migrations ແລະ build ສຳເລັດ, ໃຊ້ `pnpm auth:bootstrap` ເພື່ອສ້າງຜູ້ດູແລທຳອິດໃນການພັດທະນາ. ຊື່ຜູ້ໃຊ້ແມ່ນ `admin`; ລະຫັດຊົ່ວຄາວຢູ່ `.local/admin-access.json`. ໄຟລ໌ນີ້ເປັນຂໍ້ມູນລັບ, ບໍ່ຖືກເກັບໃນ Git ແລະ ບໍ່ຖືກໃຫ້ບໍລິການຜ່ານເວັບ.

ເປີດ http://127.0.0.1:5173/sign-in?auth=real, ເຂົ້າລະບົບເພື່ອໄປ Dashboard; ປ່ຽນລະຫັດໄດ້ໃນໜ້າບັນຊີ. ລະຫັດໃໝ່ຕ້ອງມີ 6–128 ຕົວອັກສອນ. ລະຫັດຊົ່ວຄາວໃນໄຟລ໌ຈະໃຊ້ບໍ່ໄດ້ຫຼັງຈາກປ່ຽນແລ້ວ.

ຖ້າມີຜູ້ດູແລແລ້ວ, ຄຳສັ່ງ bootstrap ທຳມະດາບໍ່ປ່ຽນລະຫັດເກົ່າ ແລະ ບໍ່ສ້າງຊ່ອງເຂົ້າໃໝ່.

## ຜູ້ດູແລບັນຊີ

1. ເຂົ້າໜ້າ **ຜູ້ໃຊ້** ເພື່ອສ້າງບັນຊີດ້ວຍຊື່ຜູ້ໃຊ້ ແລະ ຊື່ສະແດງ.
2. ລະບົບຈະສະແດງລະຫັດຊົ່ວຄາວພຽງຄັ້ງດຽວ. ສົ່ງໃຫ້ຜູ້ຮັບຜ່ານຊ່ອງທາງທີ່ບໍລິສັດກຳນົດ.
3. ເພີ່ມສະມາຊິກພະແນກແຍກຈາກບົດບາດອ່ານ/ແກ້ໄຂຂໍ້ມູນ.
4. ໃຊ້ **ອອກລະຫັດຜ່ານໃໝ່** ເມື່ອຜູ້ໃຊ້ລືມລະຫັດ. ລະບົບບໍ່ສາມາດເປີດເບິ່ງລະຫັດເກົ່າໄດ້.
5. **ລະງັບບັນຊີ** ຈະເຮັດໃຫ້ session ເກົ່າໃຊ້ API ຕໍ່ບໍ່ໄດ້.

ຜູ້ດູແລທີ່ເປີດໃຊ້ຄົນສຸດທ້າຍບໍ່ສາມາດຖືກລະງັບ ຫຼື ຖອນບົດບາດຈົນບໍ່ເຫຼືອຜູ້ດູແລໄດ້. ການປ່ຽນບັນຊີ ແລະ ສິດຖືກບັນທຶກໃນ audit.

## ບົດບາດ

| ບົດບາດ/ສິດ | ຄວາມໝາຍ |
|---|---|
| `portal_admin` | ຈັດການບັນຊີ, ອົງກອນ, ບົດບາດ ແລະ audit; ບໍ່ໃຫ້ສິດອ່ານຂໍ້ມູນວຽກທັງໝົດອັດຕະໂນມັດ |
| `resource_viewer` | ເບິ່ງລາຍການຂອງພະແນກທີ່ກຳນົດເປັນ scope |
| `resource_editor` | ເບິ່ງ, ສະແດງຄວາມເຫັນ ແລະ ແກ້ໄຂພາຍໃນ scope; ບໍ່ໃຫ້ສິດແບ່ງປັນ/ດາວໂຫຼດອັດຕະໂນມັດ |
| ເຈົ້າຂອງລາຍການ | ຈັດການລາຍການຂອງຕົນ; ການດາວໂຫຼດໃຊ້ກັບເອກະສານເທົ່ານັ້ນ |
| ການແບ່ງປັນລາຍການ | ລະບຸຜູ້ໃຊ້ ຫຼື ພະແນກ ແລະ ເລືອກ `view`, `comment`, `edit`, `download` ຫຼື `manage_access` |

ການແກ້ໄຂ/ດາວໂຫຼດ/ຈັດການສິດຕ້ອງມີສິດເບິ່ງລາຍການນັ້ນດ້ວຍ. ສິດຂອງພະແນກໃຊ້ສະເພາະສະມາຊິກທີ່ມີຜົນໃນປັດຈຸບັນ ແລະ ພະແນກທີ່ເປີດໃຊ້.

CEO → ການເງິນ/ຫ້ອງການ, CFO → ປະຕິບັດງານ/ໄອທີ, ຄະນະບໍລິຫານ → ກວດສອບ. ສາຍລາຍງານ ແລະ ການຮ່ວມມືບໍ່ແມ່ນການມອບສິດອ່ານ. ຕຳແໜ່ງ CEO/CFO ອ້າງອີງ ID ຂອງຜູ້ດຳລົງຕຳແໜ່ງ; ບໍ່ hardcode ຄົນ. ການ @ເອີ້ນເຖິງຈະເຊື່ອມໃນ Phase 03.

## session ແລະ ລະຫັດຜ່ານ

- ໝົດອາຍຸສູງສຸດ 8 ຊົ່ວໂມງ; ໝົດອາຍຸຫຼັງບໍ່ໃຊ້ງານ 30 ນາທີ.
- ຕົວເລືອກຈື່ການເຂົ້າໃຊ້ອອກ cookie ທີ່ມີເວລາສູງສຸດ 8 ຊົ່ວໂມງ; ບໍ່ໄດ້ຍົກເວັ້ນການໝົດອາຍຸຈາກການບໍ່ໃຊ້ງານ. ຖ້າບໍ່ເລືອກ ຈະໃຊ້ session cookie ຕາມການຈັດການຂອງ browser.
- ຈຳກັດ 10 ຄັ້ງຕໍ່ຊື່ຜູ້ໃຊ້ ແລະ 60 ຄັ້ງຕໍ່ IP ໃນ 15 ນາທີ; ການເຂົ້າສຳເລັດລ້າງຕົວນັບຂອງຊື່ຜູ້ໃຊ້ນັ້ນ.
- Argon2id: memory 19,456 KiB, time cost 2, parallelism 1. ຕ້ອງວັດພາລະວຽກ ແລະ ປັບໃຫ້ເໝາະກັບ server ກ່ອນ production. [ຄຳແນະນຳ OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)
- ບໍ່ເກັບ password, cookie ຫຼື token ໃນ console, audit metadata ຫຼື localStorage.

## ກູ້ຄືນຜູ້ດູແລໃນການພັດທະນາ

ຜູ້ຄຸ້ມຄອງເຄື່ອງທີ່ມີສິດເຂົ້າ `.env` ແລະ ບັນຊີ migration ສາມາດໃຊ້:

```sh
pnpm auth:bootstrap --recover
```

ຄຳສັ່ງນີ້ມີຜົນກັບບັນຊີ `admin` ເດີມໃນຖານຂໍ້ມູນ local ທີ່ກຳນົດເທົ່ານັ້ນ, ຖອນ session ເກົ່າ, ບັງຄັບປ່ຽນລະຫັດ ແລະ ບັນທຶກ audit. ບໍ່ແມ່ນ endpoint ໃຫ້ຜູ້ໃຊ້ທົ່ວໄປເອີ້ນ. ຂັ້ນຕອນ recovery ໃນ production ຕ້ອງກຳນົດຜູ້ຮັບຜິດຊອບ ແລະ ທົດສອບຢ່າງແຍກຕ່າງຫາກ.

## ການຕັ້ງຄ່າ deployment

`APP_ORIGIN` ຕ້ອງເປັນ origin ທີ່ໃຊ້ຈິງ ແລະ ບໍ່ມີ path. ໃນ production ບັງຄັບ HTTPS ແລະ cookie `Secure` ຊື່ `__Host-lapnet_session`. HTTP ອະນຸຍາດສະເພາະ loopback ໃນການພັດທະນາ.

`API_TRUST_PROXY=1` ໃຊ້ໄດ້ສະເພາະ API ທີ່ຢູ່ຫຼັງ proxy ທີ່ຄວບຄຸມໄດ້ໜຶ່ງຊັ້ນ. Nginx ຕ້ອງຂຽນທັບ `X-Forwarded-For` ດ້ວຍ IP ຂອງ client ແລະ ຫ້າມເປີດ API port ໃຫ້ຜູ້ໃຊ້ຂ້າມ proxy.

Backup ຕ້ອງລວມບັນຊີ, password hash, ບົດບາດ ແລະ audit ໃນ PostgreSQL. ກ່ອນເປີດໃຊ້ຫຼັງ restore ຄວນຖອນ session ທີ່ກູ້ກັບມາ. ສິດ host/root ຍັງສາມາດເຂົ້າເຖິງຖານຂໍ້ມູນໄດ້; audit ໃນແອັບບໍ່ແມ່ນຫຼັກຖານທີ່ host administrator ແກ້ບໍ່ໄດ້.

## ໂໝດສະແດງຕົວຢ່າງຕາມຄຳຂໍລ່າສຸດ

ໃນ development, ປຸ່ມໜ້າ Login ເຂົ້າໜ້າຕົວຢ່າງໄດ້ທັນທີໂດຍບໍ່ກວດຊ່ອງກອກ. ບໍ່ສົ່ງ password ແລະ ບໍ່ສ້າງ server session. ໜ້າຈັດການໃນໂໝດນີ້ໃຊ້ຂໍ້ມູນຕົວຢ່າງ, ບໍ່ປ່ຽນບັນຊີ/ສິດຈິງ.

API ຈິງຍັງກວດບັນຊີ ແລະ ສິດ. Production build ບໍ່ເປີດໂໝດນີ້. ເພື່ອທົດສອບ Login ຈິງໃນ development, ໃຊ້ `/sign-in?auth=real` ຫຼື ຕັ້ງ `VITE_ENABLE_UI_PREVIEW=false` ແລ້ວຮັນ web ໃໝ່. ສະຖານະ preview ຢູ່ sessionStorage ເປັນ flag ທົ່ວໄປ; ບໍ່ເກັບ password ຫຼື token.
